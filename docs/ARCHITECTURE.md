# 架构与同类项目对照

## 当前决定

一个仓库、三个独立任务入口、共享18张基础方法卡、6张创新机制卡和8维判断规则。默认每次一次模型调用，无自动多Agent协作。opportunity加载8张基础卡与A+B规则，concept加载7张基础卡与B规则，validation加载6张基础卡与C规则；只加载相关判断维度。

使用层是三个专用Agent；技术实现是指令、输入输出契约和通用执行器。没有模型微调，也没有自治工具循环。AGENT.md可独立复制使用；它不是已安装的宿主插件，纯对话模式没有程序核查。

项目及对话入口由guidance.py与data/guidance中的共享来源生成，生成一致性随发布检查执行。机制草案在一次调用内形成，不增加模型调用次数。

代码层：tasks.py管理任务输入、提示词选择、专用输出、核查和报告；core.py保留完整项目历史与共享证据函数；provider.py提供可指定Schema的单次Responses调用；cli.py提供统一命令。

API提交使用保守Schema子集，本地仍检查长度、数量、范围及引用。输入摘要绑定程序版本和任务。模型不能修改输入证据台账，也不拥有文件执行、网页抓取或付费实验工具。

这些参考不能证明拆分必然提高质量。现有差异是更集中于产品方向和实体交付约束、证据门槛及实验预算；是否优于通用产品管理工具仍需对照测试。

## 后续拆分原则

独立输入、独立交付、独立评价的任务才拆成Agent。人群分析、场景分析、证据等级等继续作为方法组件。不同Agent出现独立用户群、依赖或发布节奏后才拆仓库。

各次调用到新目录，禁止并发写同一输出目录。无多人数据库事务、自动恢复、联网抓取或生产托管。扩展这些能力必须先有明确使用需求。
