# 效果评测与社区试用

工具交付质量与终端商业结果分开。77项程序测试检查结构、证据范围、预算、硬约束、IO、请求行为与历史资料日期。它们使用构造记录，不能证明模型不会幻觉，也不用于推断业务收益。

开源发布的验收重点是：有依据的方向、可比较的方案、清楚的资源假设和可执行的下一步。企业实际决定投入资金、人员、物料、时间与团队并执行，才会产生终端结果；这不作为工具发布前置条件。以下模型和使用者评测用于改进工具自身质量，可随公开试用持续开展。

## 已准备、尚未执行的模型情境

[evaluation-cases.json](../examples/evaluation-cases.json) 包含8个情境：零证据、伪创新、模拟用户、兴趣与采用冲突、硬条件失败、共享预算、材料内指令注入、旧结论被新反馈推翻。

这些是评测设计，不是已跑通的模型成绩。每个情境要补成固定输入，使用同一模型对照：普通任务提示、v0.1完整模式、v0.2单任务。记录模型名、日期、输入输出、耗时、token用量与人工修改时间；调用费用依实际账单，不凭token虚构金额。

## 人工盲评

将三种输出随机编号，由未参与生成的评审按以下项判断可用／需修改／不可用：事实与引用忠实；用户—问题—替代—产品关系；解决机制差异；反证处理；实验能否否定假设；费用和停止条件；交付能否直接执行。

任何捏造真实记录、忽略已知硬失败、把模拟用户算真实样本的输出均标为严重失败。其他阈值先在小样本试用中校准，不预设通用成功率。

## 外部首次使用

建议首轮招募5–10名目标使用者作探索性试用，不作统计推断。只给README与一个任务，观察能否自己完成、卡在哪、需要改多少、是否愿意再次使用。分别收集三个入口的问题标签。

## 商业有效性

选择有真实结果的匿名成功和失败任务复盘，先隐藏后续结果给Agent，再比对它是否识别关键未知和更便宜的验证；这是回溯检验，仍有选择偏差。之后开展前瞻试用，记录实际投入、被停止的方向、人工时间和后续采用行为。

GitHub反馈检验工具可用性；消费者、采购者或付费者的真实行为才检验产品方向。星标数和漂亮报告均不能替代这两类验证。

历史案例可按[重演与日期审查流程](HISTORICAL_EVALUATION.md)执行。去品牌不等于模型没见过答案；回放对应度不得写成市场预测准确率。
